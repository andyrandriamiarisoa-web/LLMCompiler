Takeaway 01

          
A plan is a graph, not just a list

          
Task numbers make results addressable. A reference such as $1 says that a task uses the result from task 1.

        

        

          
Takeaway 02

          
Parallel does not mean “everything at once”

          
Independent work can overlap. Work that needs an unfinished result must wait; the longest dependency chain limits the speed-up.

        

        

          
Takeaway 03

          
A fast plan can still be a bad plan

          
If a needed dependency is missing, the scheduler cannot know to wait. Correctness matters as much as speed.

        

      


      

        

          
A few useful words

          
Tiny glossary

          
Open a term when you need it. You do not have to memorize these.

        

        

          Tool / action
          
A capability the assistant can call, such as searching a source or using a calculator. A tool's result is called an observation in this project.

        

        

          Task ID and $1
          
Each planned action gets a number. In this repository, a reference like $1 in a later action's arguments is how the parser spots a dependency on action 1.

        

        

          Dependency
          
A result that must exist before a task can run. It is like needing the ingredients before following a recipe step.

        

        

          Critical path
          
The slowest chain of dependent tasks. Even if other tasks run alongside it, this chain sets the earliest time all work can finish.

        

        

          Join
          
The step that gathers finished task results so the LLM can answer the user. Here it is drawn as a final node; it is not another search tool.

        

        

          Latency and cost
          
Parallel calls can reduce elapsed waiting time, but they do not automatically make every tool call free or reduce total work. Actual latency and cost depend on the model, tools, and workload.
